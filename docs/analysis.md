## 2. 文字编码

- `.ai` 和 `.cit` 里的文字、exe 里的所有中文字符串都是 **GBK（GB2312 范围）简体**。用 Big5 解码会在第一个汉字附近就报错。
- 游戏界面里的繁体字（机会卡、繁体台词、菜单 `Menu_f.pic`）都是**画在图片里的**，没有 Big5 文字数据。
- 字库 `Font/H16_f` 也是按 GB2312 编码排列，只是字形画成了繁体（例如“币”画成“幣”）。也就是说，原版的“繁体版”是用 GBK 编码显示繁体字形，而不是用 Big5。
- 导出的所有 JSON / TXT 都是 UTF-8；CSV 是带 BOM 的 UTF-8，Windows 上用 Excel 直接打开不会乱码。

## 3. 图片格式

### 3.1 调色板 `.col`

776 字节 = 8 字节头 + 256 × RGB（每通道 8 位）。

- `Sprite/1940.col`：游戏里几乎所有图片用这一套。
- `Sub/Main.col`：主菜单、选人界面、战役按钮用这一套。导出工具对 `Sub/` 里的每个文件按“相邻像素颜色是否平滑”自动选择，选择结果记在每张图的 JSON 里。
- `1940_bak.col`、`1940_org.col`：和 `1940.col` 只差 7 个颜色，应该是调色时的备份。

### 3.2 换色表 `Sprite/Color.idx`

2304 字节 = 9 张 × 256 字节的颜色映射表。第 0 张是原样；第 1–8 张只改色号 56 和 184–191，把它们换成不同颜色。用途是把旗子、地块标记染成各个玩家的颜色。哪张表对应哪个玩家还没确认。

### 3.3 单图 `.pic`

```
32 字节头（8 个 int32，小端）:
  [0] x       屏幕位置（界面元素用）
  [1] y
  [2] 锚点 x
  [3] 锚点 y
  [4] 数据长度（字节）   == 文件大小 - 32，所有文件都对得上
  [5] 压缩方式  0 = 原始像素  1/2 = 行程压缩（两者解码方式相同）
  [6] 高
  [7] 宽
然后是像素数据
```

行程压缩按行编码，每段不跨行，只有三种控制字节：

| 字节 | 含义 |
|---|---|
| `F9 n` + n 字节 | n 个不透明像素（色号） |
| `FA n` | n 个全透明像素 |
| `F8 n` | n 个“阴影”像素：不带数据，游戏里用来压暗底下的画面 |

导出时，透明像素 → alpha 0，阴影像素 → 半透明黑（alpha 110）。114 个 .pic 全部按这个规则精确解到 宽×高 像素。

尺寸举例：全屏图 640×480（机会卡、胜利/破产画面、菜单），立绘约 280×420，按钮几十像素。

### 3.4 精灵 `.spr`

```
文件头 16 字节: int32 默认组, int32 组数, 2 个 int32（看起来是未初始化的内存，无意义）
每组:   int32 组参数, int32 帧数
每帧:   int32 前缀 + 32 字节帧头（与 .pic 相同）+ 像素数据
```

- 一“组”一般是一个**朝向**（建筑、走路的人都是 4 组 = 4 个方向），或者一组按钮状态（普通/悬停/按下 = 3 帧）。
- 走路的角色：帧头 [0] 和帧前缀里存的是每帧的位移（±5/±6 像素），8 帧一个循环。
- 建筑：一栋楼按等距格子切成几条竖条，每条是一帧，帧头 [2][3] 是锚点。2×2 占地的楼常有 2 帧是 2×2 像素的空占位。
- 174 个 .spr 全部按此结构精确解析到文件末尾。

导出方式：每个 .spr 导出**一张拼图**（每行一组，每列一帧）+ 一个 JSON，记录每帧在拼图里的矩形、锚点、前缀。这个格式可以直接在 Godot 里用 `AtlasTexture` / `SpriteFrames` 切。`Build/` 的建筑另外导出 `*.preview.png`，是把切条按锚点拼回完整的楼（4 个朝向并排）。多数建筑拼得严丝合缝；花园洋房、小洋楼这类 3 条的建筑还有细小接缝，因为准确的拼接规则要看游戏绘制代码，这次没有追。

### 3.5 Photoshop 原稿 `WP/*.PCC`

文件头是 `8BPS`，就是 PSD。640×480，RGB / RGBA，有的带图层。内容是故事插图和机会卡的**原始真彩色稿**（例如 `J1.PCC` 就是 `Chance1.pic` 的原图），比游戏里 256 色的版本清楚。导出的是合成后的整图（`extracted/wp/`）。

### 3.6 字库 `Font/`

- `Asc16`：4096 字节，256 个 8×16 英文字符，每字 16 字节。
- `H16_j`：267616 字节，标准 HZK16 格式的 16×16 简体字库，每字 32 字节，第 `(区-0xA1)×94 + (位-0xA1)` 个字。
- `H16_f`：同样排列，字形是繁体。

导出成整张字表图片（`extracted/fonts/`）。导出工具画地图示意图时，标签就是用这套原版字库画的。

### 3.7 过场动画 `Sprite/*.avi`

Cinepak 视频 + PCM 声音。`North.avi` 640×460，8 秒；`Pt.avi` 640×282，21 秒。已转成 Ogg Theora（`extracted/video/*.ogv`），Godot 4 的 `VideoStreamPlayer` 能直接播。

### 3.8 音频 `Sound/`

- 74 个 WAV：单声道 22050 Hz，8 位（41 个）或 16 位（33 个）PCM。Godot 能直接导入。
- 11 个 MIDI：背景音乐（`Game1–5`、`Intro`、`Paimai` 拍卖、`Jiaoyi` 交易、`Jeishu` 结束等）。**Godot 4 没有内置 MIDI 播放**，要用的话得先转成 OGG（需要 SoundFont 渲染），或者装 MIDI 插件。
- 原样复制到 `extracted/audio/`（文件名改成小写），`_audio.csv` 列出格式和时长。

## 4. `Map.lib` 和 `Houses.lib` 到底是什么

两个文件的开头 1.5–2 MB 是 raw deflate 压缩流，后面接着一大段无关的残留数据（`Map.lib` 后面是 x86 机器码，`Houses.lib` 后面有按 16 KB 对齐的 WAV 文件头，像是磁盘上的旧数据）。

解压后：

- `Map.lib` → 以 `VCPCH0` 开头，是 **Visual C++ 预编译头文件**，时间戳 1997-01-22。
- `Houses.lib` → 以 `Microsoft C/C++ program database 2.00` 开头，内容是 `/bsc/src/D:\MyProjects\1940\*.cpp` 这类路径，是 **VC++ 浏览信息库**。

`1940.exe` 里没有任何地方引用 `.lib`，游戏不会读这两个文件。它们应该是开发者打包光盘时混进来的编译缓存，被改成了现在的名字。

但它们很有用：预编译头里保留了游戏头文件 `const.h`、`city.h`、`block.h`、`building.h`、`person.h`、`brain.h` 里的**所有标识符**，按声明顺序排列。这次能把 `.cit` 里的数字对上含义，主要靠它。例如：

- `CITY_PROPERTY` 结构的字段顺序（建房成本、各级租金、空地价）
- 地块类型 `BLOCK_CLASS_TYPE`、建筑类型 `BUILDING_CLASS_TYPE`、建筑图种类 `BUILDING_SPRITE_KIND`
- 行业组 `COMPANY_GROUP`、角色状态 `PERSON_STATE`、台词触发条件 `SENTENCE_CONDITION`
- AI 参数结构 `PERSONAL_VALUE` 和 AI 函数名（`getPriceIThink`、`tryToTrade`、`bestSiteToBuild`……）

导出的只有标识符列表和源码文件列表（`extracted/devfiles/`），解压出的二进制没有保存。源码共 27 个 .cpp，包括 `Brain.cpp`（AI）、`PubSell.cpp`（拍卖）、`Trade.cpp`（交易）、`racecourse.cpp`（赛马）、`cheat.cpp`（作弊码）。

## 5. 地图 `.cit` 格式

读取顺序来自 exe 里的 `City::load` 函数（反汇编 `1940.exe` 得到），字段名来自预编译头。

```
CITY_PROPERTY（88 字节）
  char  name[16]          城市名（GBK）
  char  ai_file[16]       AI 配置文件名
  int32 × 14              建房成本 6 项、租金 7 项、空地价 1 项（见下表）
int32 origin_x            地图 x 坐标起点（负数）
int32 size                地图是 size × size 的格子
uint8 has_blocks
size × size 个地块记录    x 从 origin_x 开始，y 从 0 开始
128 个建筑槽位            int32 建筑类型，0 = 空，否则接着读建筑数据
6 个玩家槽位              uint8 标志，0 = 空，否则接着读玩家数据
```

存档也是同样的格式（exe 用同一个函数读写）。

### 5.1 地块记录

每块先是 int32 类型号，后面字段由各类自己的 `load()` 读取，子类先读父类的字段。

| 类型号 | 类型 | 用途 | 记录内容（类型号之后） |
|---|---|---|---|
| 7 | NULL_BLOCK | 地图外的空白 | x, y（各 int16） |
| 10 | SURFACE | 草地等地表 | x, y, 地表图帧号, 1 个 int16, 是否有装饰(uint8) [+ 装饰号 int32，树木] |
| 9 | ROAD | 道路（棋子走的格子） | x, y, 道路图帧号, 1 个 int16 |
| 5 | CROSS_ROAD | 路口 | 同 ROAD + int32（低 2 位 = 箭头朝向，其余 = 优先方向） |
| 6 | LAND | **可买的空地**（路边） | x, y, 所属建筑号, 帧号, **所有者**, 1 字节标志, **街道名**(32 字节), 2 个 int32 百分比 |
| 4 | COMPANY_BASE | 企业占的格子 | x, y, 所属建筑号, 帧号, 所有者 |
| 8 | PUBLIC_BASE | 公共建筑占的格子（银行、教堂……） | x, y, 所属建筑号, 帧号 |
| 1/2/3 | BASE / BLOCK / BUYABLE_BASE | 地图文件里没出现 | — |

所有者是角色 ID，8 表示无主。

### 5.2 建筑记录

先读子类字段，再读所有建筑共有的字段：朝向(0–3)、所有者、建筑图种类、32 字节未初始化内存（发行版文件里是垃圾值）、显示名称(32 字节)。

| 类型号 | 建筑 | 额外字段 |
|---|---|---|
| 6 | COMPANY 企业 | 行业组、广告语（变长字符串）、**价格**、**租金** |
| 10 | HOUSE 民宅（玩家建的房子） | 房屋等级 + 1 个 int16 |
| 8/11/12/16/17 | 特许建筑：黑帮(11)、算命铺(12)、当铺(16) 等 | 1 个 int16 |
| 1 BANK 银行、4 CHANCE 运气、5 CHURCH 教堂、9 GOVERNMENT 市政厅、13 PARK 公园、15 RACE_COURSE 赛马场、18 TAX_HOUSE 税务局、19 WATCH_MAN_HOUSE 巡捕房、3 CASINO 赌场 | 无 |

建筑图种类（`sprite_kind`）对应 `Build/` 里的文件，顺序存在 exe 里，已全部对上，例如 0 平房 `Ping_f`、5 别墅 `Bie_s`、10 火车站 `Huo_c`、11 码头 `Ma_t`、22 夜总会 `Yie_z`、25 银行 `Yin_h`、30 赛马场 `Sai_m`。完整列表在 `tools/render_city.py` 的 `KIND_FILES`。

### 5.3 玩家记录

是否 AI、手牌列表、角色 ID、起始格子、名字、两个金额字段（开局都是 2000，应该是现金和存款），还有几个没确认含义的 int32。

### 5.4 地图结构的特点

原版**不是一圈环形棋盘**，而是一张 45° 斜放的方格城市，道路组成路网，有多个**十字路口**（玩家在路口选方向或按箭头走）。可买的空地排在道路两侧，企业和公共建筑占 2×2 格子。上海图是 54×54 格，有 151 格道路、9 个路口、64 块空地、26 栋建筑。

每张地图导出了两张参考图：

- `*_map.png`：俯视示意图，按格子类型着色，空地颜色深浅表示地价高低，标出建筑名。
- `*_iso.jpg`：用原版地表、道路、建筑图块拼出的等距画面，接近游戏里的样子。道路方向已核对；建筑整体放置的规则是根据画面效果推出来的，不是从游戏绘制代码读出来的，个别建筑可能偏几个像素。

## 6. 原版数据的大致结构

### 6.1 城市参数（单位：万圆）

所有地图共用一套“房屋等级”，每张地图有自己的价格表。自由模式 4 张城市的参数几乎一样：

| 字段 | 含义 | 上海 | 金县（战役第一关） |

| uCost_HOTEL_HOUSE | 旅社造价 | 100 | 80 |
| uCost_FLOOR_HOUSE | 小洋楼造价 | 140 | 100 |
| uCost_VILLA_HOUSE | 别墅造价 | 200 | 120 |
| uCost_UPDATE | 升级费用 | 60 | 30 |
| uCost_FUNCTION_HOUSE | 特许建筑造价（黑帮/算命铺/当铺） | 80 | 50 |
| uRent_BLANK_LAND | 空地租金 | 15 | 10 |
| uRent_FLAT_HOUSE | 平房租金 | 30 | 20 |
| uRent_HOTEL_HOUSE | 旅社租金 | 60 | 30 |
| uRent_SUPER_HOTEL_HOUSE | 旅馆租金 | 80 | 40 |

| uRent_VILLA_HOUSE | 别墅租金 | 150 | 80 |
| uPrice_BLANK_LAND | 空地基准价 | 80 | 50 |

建房方式（从预编译头里的按钮名 `pBtnPingFang / pBtnGongYu / pBtnXiaoYangLou / pBtnBieShu / pBtnUpdate / pBtnTeXu` 和 exe 的说明文字推断）：在空地上**四选一**建平房、旅社（公寓）、小洋楼或别墅；旅社可以**升级**成旅馆，小洋楼可以升级成花园洋房（说明里带“+”的两项，升级费 `uCost_UPDATE`）；另外拿到市政厅特许后可以建黑帮、算命铺、当铺（`uCost_FUNCTION_HOUSE`）。界面上的说明格式是：

```
            造价     租金
空地:       %4d    %4d
平房:       %4d    %4d
旅社:       %4d    %4d
旅馆:      +%4d    %4d
小洋楼:     %4d    %4d
花园洋房:  +%4d    %4d
别墅:       %4d    %4d
```

全部城市参数在 `extracted/data/cities/_summary.csv`。

### 6.2 地块

每块空地有街道名和一个**地价系数**（百分比）：

- 空地售价 = 系数 × `uPrice_BLANK_LAND` ÷ 100
- 空地租金 = 系数 × `uRent_BLANK_LAND` ÷ 100

这两个公式是从 exe 显示地块信息的代码里读出来的。上海的系数从 80（顺昌路、西藏北路）到 240（南京路），同一条街的几块地系数相同，按街道分组，相当于大富翁的“颜色组”。导出的 `*_lands.csv` 已经算好了每块地的售价和空地租金。

地块里还有第二个百分比（例如万航渡路 130 和 140），后来反汇编确认它是**建房成本系数**：建房造价按它计算，见 `docs/original_rules.md`。

### 6.3 企业

上海有 16 家企业，分属行业组：运输（上海站、码头、电车公司）、娱乐（夜总会）、商业（百货、洋行）、纺织（织厂）。每家有价格（360–560）、租金（90–130）和一句广告语（例如先施百货“本店宗旨：收罗全球百货”）。exe 里有“控制所有娱乐业”“控制所有码头”这类战役目标，说明同一行业组的企业有组合效果。导出在 `*_buildings.csv`。

### 6.5 角色状态

源码里的 `PERSON_STATE` 枚举：未参加、破产、正常、小偷、纵火犯、抢劫犯、免付租金、付租加倍、付租减半、坐牢、在公园、慈善（自己的产业不收租）、信徒。大部分由机会卡触发。

### 6.6 机会卡（34 张）

文字画在 `Sprite/Chance1–34.pic` 里，已手工转录到 `extracted/text/chance_cards.json`（保留原图繁体字，附效果分类）。类型分布：

- 现金增减：拾到 100 万、擦皮鞋 1 万、被富婆相中 300 万、发现古董 1000 万、逛夜总会 −100 万、随地吐痰罚 30 万……
- 向每人收钱 / 付每人钱：抗日募捐收每人 50 万、丑行败露付每人 100 万
- 坐牢：3 天或 5 天
- 持续一周的状态：小偷、纵火犯、抢劫犯、免费旅游、加倍消费、半价旅行、慈善
- 地产变化：最贵地产被没收、抵押物业被收回、一处房屋被砸、所有房产贬值/土地增值 10%、所有房产升一级、房屋倒塌
- 银行：倒闭存款丢失、强行扣留应付款项

源码里有 `chance1`–`chance30` 30 个函数（函数名见于预编译头），另外 4 张卡可能属于 `showBuildChance1/2`、`showMortgageChance`、`showGetRentChance` 这几个特殊函数，没确认。卡面效果是按文字理解的，具体数值以后可以对照 exe 再核实。

### 6.7 台词（8 角色 × 12 句）

画在 `Sentence/*.spr` 里，已转录到 `extracted/text/speech_lines.json`。12 帧的顺序正好对应源码的 `SENTENCE_CONDITION`：

付高额租金 / 付少量钱 / 交好运 / 倒霉 / 进巡捕房 / 建成别墅 / 交易成功 / 交易被拒 / 得到施舍 / 被偷 / 偷到钱 / 脱险

例如进巡捕房时：四毛“凭啥哩？”，金如山“我儿子是保长！”，包德利“我要找律师”，发达而“WHY？”。发达而全说英文，董莺雨中英混杂（“书中自有gold屋”）。这套“同一事件、不同角色不同反应”的结构可以直接沿用到四方来财。

### 6.8 AI 性格

`Ai/*.ai` 是带注释的 GBK 文本，每个角色 12 个参数，全部导出成 JSON 和 CSV（`extracted/text/ai/`）。

| 参数 | 原注释 |
|---|---|
| buyLandExpect | 越小，越喜欢买土地 |
| buyCompanyExpect | 越小，越喜欢买企业 |
| keepCashExpect | 一般情况下希望保留的现金数 |
| keepCashDiff | 越小，进入银行越频繁 |
| buildHouseExpect | 越小，越喜欢建房 |
| mortgageExpect / unmortgageExpect | 越小，越喜欢抵押 / 赎回 |
| removeExpect | 越小，越喜欢拆房 |
| intendToAddMuchMoney | 越大，在拍卖中越喜欢（加价） |
| acceptableDiffenceInTrade | 交易中可以接受的价值差（百分比） |
| tradeCycle | 寻求交易的平均周期 |
| maxInvestment | 资金低于 总资产×此值/100 时不再投资 |

例：金如山（标准配置）`keepCashDiff=5`、拍卖加价意愿 10、交易可接受差价 −30%，很吝啬；陈玛丽、冯全篾拍卖加价意愿 80。

原版 AI 只是一组固定阈值，不看局势，这正是设计文档里说的“AI 很蠢”的原因。另外：地图引用的 `shanghai.ai` 在光盘里不存在，exe 有提示“load 'standard.ai' instead”，会退回标准配置；`Story12.cit` 还把文件名错写成 `jianxian.ai`。

### 6.9 战役模式

3 条战役共 20 关，关卡说明在 exe 里，已对应到地图文件，导出在 `extracted/text/campaigns.json`：

- 四毛（Story11–17）：金县建旅馆 → 金县让金如山破产 → 银城控制所有码头 → …… → 上海击败所有对手
- 冯全篾（Story21–27）：金县 → 元宝山一个月击败发达而和包德利 → 溪口镇 → …… → 上海击败赛珍珠
- 董莺雨（Story31–36）：溪口镇一个月资产达一千万 → 溪口镇控制所有书局 → …… → 上海击败所有对手

胜利条件类型：击败某人 / 所有人、限时、建成某建筑、控制某行业、资产达标、保护盟友不破产。这些可以作为四方来财单人战役的参考。各关对话也在 `exe_strings.json` 里（每关的对话存在关卡说明旁边，倒序存放）。

第一版报告里没确认的字段，在后续反汇编原版规则时大多查清了（详见 `docs/original_rules.md`），解析器和导出文件已经改用下面的字段名：

| 位置 | 结论 |
|---|---|
| LAND `+0x38`（原 `land_flag`） | `mortgaged`：1 = 已抵押 |

## 10. 对 Godot 重做的建议

### 数据

1. **价格表直接用 JSON**。`extracted/data/cities/*.json` 里的 `property` 和地块百分比，可以整理成四方来财自己的 `data/cities/<城市>.json`：每块地 = 街道名 + 颜色组 + 价格系数。原版“同一条街系数相同”的做法正好对应设计文档里的颜色组规则。
2. **把计算公式和数值分开**。原版是“城市基准价 × 地块系数”，这个结构好调：改一个城市的物价只动一个数。建议保留。
3. **AI 参数**：原版 12 个阈值可以作为“性格”的初始值，但设计文档要求 AI 看局势，建议在阈值外再加一层按处境（领先 / 落后 / 快破产）切换的权重，阈值放在 JSON 里方便调。
4. **台词表结构**沿用原版：`事件类型 → 每个角色一句`，用 JSON 存文字而不是做成图片，方便以后改文案、加语言。
5. **机会卡**同理：`卡 id、标题、正文、效果类型、参数` 存 JSON，效果用一小组通用动作（加减钱、坐牢 N 天、加状态 N 回合、地产变化）组合，原版 34 张都能用这几类表达。

### 地图

6. 原版的 54×54 斜格路网很大，而且有路口分叉，这正是“一局太长”的原因之一。设计文档定的是一圈 30–40 格，建议做成**单环棋盘**，原版路网只当美术参考。
7. 如果保留等距（斜 45°）画风：原版图块是 80×40 的菱形，Godot 4 的 `TileMapLayer` 选 Isometric、格子 80×40 就能直接用来做原型，换皮时替换图片即可。
8. 建议用 Godot 的 Resource 或 JSON 描述棋盘：`格子序号 → 类型（地块 / 机会 / 银行 / 监狱……）+ 屏幕坐标`，逻辑只认序号，不认画面，换地图时只换这份描述。

### 美术和音频

9. 原版图片都是 256 色调色板，已全部转成透明 PNG，可以直接做占位素材。精灵拼图 + JSON 帧数据能用脚本批量生成 `SpriteFrames`。
10. 阴影像素导出成了半透明黑。如果想要原版的阴影效果，可以在 Godot 里单独放一层阴影。
11. 背景音乐是 MIDI，Godot 不能直接播。原型阶段建议先转成 OGG（例如用 FluidSynth + 一个 General MIDI 音色库）或者先不用。
12. 原版素材只作参考和占位，不要放进最终发布的包里；四方来财项目里建议把 `extracted/` 当作只读参考目录，自己的素材放在 Godot 项目的 `assets/` 下，避免以后混在一起。

### 下一步

13. 阶段 2 开始前，建议先从 `extracted/` 挑出要复刻的原版规则数据（一张城市参数、一份地块表、机会卡、台词），整理成四方来财自己的数据格式，Godot 只读这份数据。
14. 如果想更精确地复刻原版规则（例如旅馆、花园洋房升级的具体加成，银行利率，拍卖流程），可以继续按这次的方法反汇编 exe 的相关函数。
